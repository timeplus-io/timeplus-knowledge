Why would a materialized view fall behind after a node restart?
Thought for 11s
weighed checkpoint replay window vs. stream compaction · 2 thinking steps · 3 tool calls
show ▸
After a restart the view resumes from its last checkpoint epoch, so it reprocesses everything recorded after that sequence number — with a long checkpoint interval this replay window is the usual cause of lag.[1]
  • Replay is unthrottled but competes with live ingest for the same pipeline slots.[1]
  • If the source stream's retention compacted past the recorded sequence, the view logs a gap warning and resumes from the earliest available offset.[2]
  • Mitigation: lower checkpoint_interval on hot views.[2]

Materialized views persist their processing position as checkpoints, so a restart resumes exactly where the query left off instead of reprocessing the stream.[1]
How it works
  • The pipeline periodically snapshots operator state plus the source stream sequence number.[1]
  • On recovery the engine restores the snapshot and replays from the recorded sequence — exactly-once into the view's target stream.[1]
  • The interval is tunable per view; shorter intervals trade write amplification for faster recovery.[2]
CREATE MATERIALIZED VIEW mv_orders
SETTINGS checkpoint_interval = 5
AS SELECT window_start, count() FROM tumble(orders, 5s) GROUP BY window_start;
